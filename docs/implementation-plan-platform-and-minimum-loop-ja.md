# 起動環境の分割と最小動作ループの実装計画

この資料は、追加レビューで指摘された「起動単位が大きすぎる」「Windows デモと
Linux/ROS などの将来環境が混ざりそう」という問題に対する実装計画です。

専門用語をなるべく避けて説明します。必要な用語は、その場で言い換えます。

## いま直したこと

今回すぐに直せる範囲として、次を行いました。

- AITuberKit の参照先が、2つの設定ファイルでズレていた問題を修正しました。
- 同じズレが再発しないよう、検証スクリプトに一致チェックを追加しました。
- 「Windows デモ」「Linux の最小確認」「WSL/ROS の実験」などを混ぜないための
  新しい説明文書 `docs/platform-profiles.md` を追加しました。
- 既存の設計文書から、この新しい説明文書へ誘導するリンクを追加しました。

## 何が問題だったか

現在の標準起動は、画面、音声、アバター、カメラ、家電操作、状態確認などを
まとめて扱います。これはデモ環境としては便利ですが、次の問題があります。

- 起動する部品が多く、どれが本当に必要なのか分かりにくい。
- Windows の画面付きデモと、Linux の軽い確認が同じ考え方に見えやすい。
- ROS のような外部センサー基盤を足したとき、判断や安全確認の責任まで混ざりやすい。
- 機能を差し替えたいとき、どこを変えればよいかが重く見える。

つまり、動作速度そのものより先に、「何をいつ起動するか」を分ける必要があります。

## これからの基本方針

今後は、起動を次の3つに分けます。

1. いつも必要な最小部分
   - 状態を持つこと
   - 記録すること
   - 危険な操作の前に止めること
   - 最小限の判断を返すこと

2. 必要な時だけ起こす部分
   - アバター表示
   - 音声入力や音声出力
   - カメラ
   - 家電操作
   - TouchDesigner や Projection Visual などの表示画面

3. 環境ごとに違う部分
   - Windows で画面付きデモをする
   - Linux で画面なしの最小確認をする
   - WSL で ROS 連携を試す
   - Ubuntu 側をセンサー専用の小さなノードとして使う

## 利用者レビューが必要な判断

以下は、実装前にレビューしてほしい項目です。

### 1. 最初に作る環境設定をどれにするか

候補は次です。

- `windows-demo`: 今の Windows PC で画面、音声、アバター、家電連携を試す。
- `linux-headless`: 画面や家電なしで、最小限「生きているか」だけ確認する。
- `wsl-ros-poc`: Windows 上の WSL で ROS 連携を小さく試す。
- `ubuntu-ros-sensor-node`: Ubuntu 側をセンサー専用の入口にする。

おすすめは、まず `windows-demo` と `linux-headless` の2つです。
理由は、現在の環境を壊さず、同時に「軽い確認」の逃げ道を作れるためです。

### 2. 最小起動に何を含めるか

最小起動は、重い画面や家電操作を含めない方が安全です。

おすすめの最小起動:

- 状態管理
- 記録
- 安全境界
- 最小の会話または応答確認

まだ含めない方がよいもの:

- カメラ
- マイク
- VOICEVOX
- アバター表示
- TouchDesigner
- Home Assistant 経由の家電操作

### 3. ROS をどこに置くか

ROS は、判断そのものや安全承認そのものにしない方がよいです。

分かりやすく言うと、ROS は「センサーやロボット連携の土台」です。
「何をしてよいかを決める頭」や「危険な操作を止める門番」ではありません。

この分け方を守ると、ROS を足しても現在の安全境界が崩れにくくなります。

### 4. 現在の標準ランチャーをいつ分割するか

現在の起動経路は、Windows デモとしては便利です。
ただし将来は、次のように分けるとよいです。

- 最小確認だけを起動する
- 表示だけを起動する
- 音声だけを起動する
- 家電操作だけを起動する
- カメラだけを起動する

一度に全部分ける必要はありません。まずは「Windows デモ用の起動経路」と明記し、
その後で必要な部品から分けるのが安全です。

## 実装順序の提案

### フェーズ1: 文書と検証の整理

目的: 設計の混線を止める。

- `docs/platform-profiles.md` を起点にする。
- `windows-demo` と `linux-headless` の草案を作る。
- 既存の標準ランチャーは Windows デモ向けだと明記する。
- 検証コマンドで「必須部品」と「任意部品」を分けて表示する。

### フェーズ2: 最小動作ループを作る

目的: 「このシステムの最小の身体動作」を小さく実証する。

例:

1. 文字入力を受ける。
2. 最小の判断を返す。
3. 表示用のイベントを作る。
4. 状態と記録に残す。
5. その結果を読み返せるようにする。

ここでは家電操作、カメラ、音声、ROS は使わなくてよいです。
小さく動く芯を先に作ると、あとで機能を足しても迷いにくくなります。

### フェーズ3: 必要時起動に分ける

目的: 起動を軽くし、使う機能だけ起こせるようにする。

候補:

- アバター表示を必要時起動にする。
- 音声入力/出力を必要時起動にする。
- カメラを必要時起動にする。
- 家電操作の橋渡しを必要時起動にする。

### フェーズ4: WSL / ROS の実験入口を作る

目的: Windows デモと ROS 実験を混ぜない。

- WSL/ROS は「下位の実行基盤」として扱う。
- ROS から来たセンサー情報は、要約して現在の状態へ渡す。
- ROS 側に判断や安全承認を持たせない。

## この計画でまだ実装しないこと

- ROS の本格実装。
- 家電操作の新しい live 証明。
- 物理デバイスが実際に動いたという証明。
- 音声やカメラの生データを保存する仕組み。
- Windows 以外の環境での完全動作保証。

## レビューしてほしい結論

まず確認してほしいのは、次の3点です。

1. 最初に作る環境設定は `windows-demo` と `linux-headless` でよいか。
2. 最小起動から、カメラ、音声、家電、アバター、TouchDesigner を外してよいか。
3. ROS は「判断する場所」ではなく「センサーやロボット連携の土台」として扱ってよいか。

この3点が合意できれば、次は小さな manifest 草案と検証コマンドに進めます。
