# Platform Profiles

この文書は、Sword Agent OS をどの種類の実行環境で動かすかを分けるための
入口です。ここでいう platform profile は「Windows で画面を出して試す」
「Linux で最小の確認だけを行う」「WSL や ROS を下位基盤として使う」
といった環境ごとの起動方針です。

この文書は実装完了の宣言ではありません。現時点では、環境ごとの考え方を
混ぜないための設計メモです。

## なぜ分けるのか

標準構成には、会話、音声、アバター、カメラ、状態確認、家電操作、表示用の
実行部品が含まれます。全部をいつも同時に起動すると、確認が重くなり、
どの部品が本当に必要なのかが分かりにくくなります。

そのため、今後は次のように分けます。

- いつも必要な最小部分: 状態管理、記録、安全境界、最小の判断経路。
- 必要な時だけ起こす部分: アバター、音声、カメラ、家電操作、表示画面。
- 環境ごとに違う部分: Windows の画面デモ、Linux の最小確認、WSL、ROS。

## 基本ルール

- platform profile は、どの環境で、どの部品を起動するかを決める。
- organ は、声、カメラ、表示、家電操作などの担当機能を表す。
- service は、実際に起動するサーバーや作業プロセスを表す。
- substrate は、複数の機能が使う下位の実行基盤を表す。例は WSL、Ubuntu、
  ROS 2 など。

substrate は、判断や安全承認の責任を持ちません。たとえば ROS 2 はセンサーや
ロボット連携の基盤になれますが、家電や物理環境を実際に動かしてよいかを
決める場所ではありません。

## 最初に定義する候補

| 候補 | 目的 | 既定で起こすもの | 既定で起こさないもの |
| --- | --- | --- | --- |
| `windows-demo` | 現在のWindows PCで画面、音声、アバター、家電連携を試す | 標準ランチャーと、選択した表示/音声/家電レーン | ROS、Linux専用ノード |
| `linux-headless` | 画面や家電なしで最小の生存確認をする | 状態管理、記録、安全境界、最小の判断経路 | カメラ、音声、アバター、家電操作 |
| `wsl-ros-poc` | Windows上のWSLでROS連携を試す | 最小確認とROS連携の実験入口 | 家電操作の実行、物理証明 |
| `ubuntu-ros-sensor-node` | Ubuntu側をセンサー担当ノードとして使う | センサー入力の要約送信 | 判断、安全承認、家電操作 |

これらは草案です。実際の JSON manifest、起動スクリプト、検証コマンドは、
別途レビューしてから追加します。

最初の草案 manifest は `manifests/platform-profiles/` に置きます。現時点では
`windows-demo.json` と `linux-headless.json` だけを置き、WSL/ROS の本格実装は
まだ行いません。

## 現在の標準ランチャーの扱い

現在の `home-control-stack` は、歴史的に標準デモ用の起動経路として育ったものです。
今後は「すべての環境で必ず使う唯一の起動方法」ではなく、
Windows demo 向けの標準ランチャーの一つとして扱います。

他の環境では、同じ状態確認や安全境界を使いながら、別の起動方法を選べるように
します。

## 実装前に決めること

次の項目は、実装前に利用者または担当者のレビューが必要です。

1. 最初に作る platform profile をどれにするか。
2. 最小起動で必須にする部品をどこまでにするか。
3. ROS や WSL を、どの範囲まで「下位基盤」として扱うか。
4. Windows demo の現在の起動経路を、どの段階で小さな起動単位に分割するか。
5. 家電操作、カメラ、音声、アバターを、それぞれいつ必要時起動に移すか。

## 次の小さな実装計画

安全に進めるなら、順番は次です。

1. この文書を設計の入口として採用する。
2. `manifests/platform-profiles/` の最小スキーマ案を作る。
3. `windows-demo` と `linux-headless` の草案だけを追加する。
4. 既存の標準ランチャーが `windows-demo` 向けであることを明記する。
5. 起動時の必須部品と任意部品を、検証コマンドで区別できるようにする。

ROS や複数センサーの実装は、その後で構いません。先に環境ごとの起動方針を
分けておくことで、Windows demo、Linux、WSL、ROS の設計が混ざりにくくなります。
